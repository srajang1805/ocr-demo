# Build a Document Intelligence Table Parser — Ur AI R&D Internship Take-Home

## Objective

Build a working, reproducible document-to-table extraction system for Japanese financial statements. The supplied input is `balance_sheet_after_correction.pdf`, a one-page Japanese consolidated balance sheet (連結貸借対照表).

The system should extract the page into a correctly structured table, preserving Japanese labels, numerical values, column headers, row hierarchy, accounting notation, and table relationships.

This is an R&D take-home assignment for a Document Intelligence & VLM internship. Prioritize measurable correctness, a clean architecture, reproducibility, and honest evaluation over unnecessary complexity.

**Do not stop at proposing an architecture. Implement the project, run it, debug it, and produce working output files.**

## 2. Implement a hybrid extraction pipeline

Use Python and appropriate libraries such as PyMuPDF, pdfplumber, pandas, Pillow, and pytest where useful. Avoid installing large dependencies unless they materially improve the solution.

Implement the following stages.

### Stage A: PDF ingestion

- Open the input PDF.
- Extract page text, words, bounding boxes, and character or span coordinates where available.
- Render pages to images when visual analysis is necessary.
- Preserve the original document and page numbering.
- Support multiple pages in the architecture, even though the supplied example has one page.

### Stage B: Layout and table reconstruction

Recover the table's logical rows and columns from text coordinates and visual alignment.

The sample contains:
- Japanese row labels.
- Two fiscal-year value columns.
- Reporting dates of March 31, 2025, and March 31, 2026.
- The unit 千円 (thousand yen).
- Hierarchical sections, including assets, current assets, fixed assets, tangible fixed assets, intangible fixed assets, and investments and other assets.
- Detail rows, depreciation rows, net-value rows, subtotals, and grand totals.
- Negative amounts represented by △.
- Dash placeholders represented by － or equivalent glyphs.
- Rows whose labels are indented to indicate hierarchy.

Use coordinates and alignment rather than assuming every row has the same number of spaces. Do not merge unrelated rows or shift values between columns.

Where appropriate, implement a fallback OCR or vision-model interface behind a separate extraction module. The core project must remain runnable without credentials. Do not claim that a VLM fallback works unless it has actually been implemented and tested.

### Stage C: Normalization

Preserve both source-faithful and normalized representations.

For monetary values, store:
- `raw`: the original extracted string, preserving meaningful notation.
- `value`: the normalized numeric value, or null when the source represents a dash or the value cannot be parsed.
- `is_negative`: whether the source denotes a negative value.
- `parse_status`: for example, `parsed`, `dash`, or `unparsed`.

Handle Japanese accounting notation carefully:
- △2,979 means -2979.
- △0 means numeric zero with a negative-sign marker retained in the raw value.
- － means a dash placeholder, not automatically a numeric zero.
- Commas in monetary values are thousands separators.

Do not silently correct or invent missing values.

For text normalization, preserve the original Japanese labels. If you add English translations, mark them as optional annotations and do not replace the original labels.

### Stage D: Hierarchical structure

Represent the document as a table with metadata and ordered rows.

Use a schema along these lines:

{
  "document": {
    "source_file": "balance_sheet_after_correction.pdf",
    "page": 1,
    "document_type": "consolidated_balance_sheet",
    "language": "ja",
    "unit": "千円",
    "columns": [
      {
        "id": "previous_year",
        "label": "前連結会計年度",
        "date": "2025-03-31"
      },
      {
        "id": "current_year",
        "label": "当連結会計年度",
        "date": "2026-03-31"
      }
    ]
  },
  "rows": [
    {
      "row_index": 0,
      "label": "現金及び預金",
      "parent": "流動資産",
      "depth": 2,
      "row_type": "detail",
      "values": {
        "previous_year": {
          "raw": "2,002,429",
          "value": 2002429,
          "is_negative": false,
          "parse_status": "parsed"
        },
        "current_year": {
          "raw": "608,281",
          "value": 608281,
          "is_negative": false,
          "parse_status": "parsed"
        }
      }
    }
  ]
}

This is an illustrative schema, not a hardcoded extraction result. Adapt it as necessary, document the final schema, and ensure the entire table is represented.

Use a stable row ID or a well-defined parent reference. Avoid ambiguous parent references when labels repeat. Preserve source row order and distinguish section headers from numeric detail rows.

## 3. Create independent ground truth

Create `ground_truth.json` by manually annotating the supplied PDF.

Requirements:
- Include every logical table row and both value columns.
- Include section headers and hierarchy information.
- Preserve the exact Japanese labels and source monetary notation.
- Distinguish dash placeholders from zero.
- Record the unit and reporting dates.
- Verify the annotation against the rendered page, not just extracted text.
- Keep ground truth separate from the extraction code.

Do not generate ground truth from the parser's own output. That would make the evaluation circular.

If any character or value is genuinely ambiguous, record the ambiguity and explain it instead of guessing.

## 4. Build a meaningful evaluation framework

Implement `evaluate.py` to compare the parser output with the independent ground truth.

Calculate and report:

1. Exact row-label accuracy.
2. Exact monetary raw-string accuracy.
3. Normalized numeric accuracy, comparing parsed numeric values.
4. Cell exact-match accuracy.
5. Row detection precision, recall, and F1.
6. Structural accuracy for row ordering and parent-child relationships.
7. Arithmetic consistency checks for applicable subtotals and totals.
8. A list of mismatches with expected value, predicted value, page, row, and column.

Define each metric precisely in the README. Explain how missing, extra, duplicated, and unparsed rows affect scoring. Avoid ambiguous denominators and silent exclusions.

Treat arithmetic checks as diagnostics, not as permission to change extracted values. Some displayed financial totals can differ from sums of displayed components due to rounding or reporting conventions.

Include a clear summary such as:

- Expected rows
- Predicted rows
- Correctly matched rows
- Expected value cells
- Exact matching cells
- Numeric parsing failures
- Structural mismatches
- Arithmetic validation warnings

Run the evaluation and report the real results. Never fabricate an accuracy percentage or claim success without execution evidence.

## 5. Produce useful outputs

The program should generate:

- `output.json`: structured table with metadata, values, and hierarchy.
- `output.csv`: flat table with stable row IDs, hierarchy, Japanese labels, row types, and the two reporting-period values.
- `evaluation.json`: machine-readable metrics and errors.
- `evaluation_report.md`: human-readable results and error analysis.

Keep the original values available even when the CSV uses normalized numeric columns.

Use UTF-8 encoding and ensure Japanese characters survive a CSV round trip. Document how to open the CSV correctly in spreadsheet applications.

## 6. Add tests

Create automated tests for:

- Parsing positive integers with commas.
- Parsing △2,979 as -2979.
- Preserving △0 while normalizing its numeric value.
- Preserving － as a dash placeholder.
- Handling whitespace and Japanese labels.
- Reconstructing two aligned numeric columns.
- Maintaining row order.
- Representing parent-child hierarchy.
- Handling empty or unparseable cells without crashing.
- Detecting duplicated and missing rows.
- Producing deterministic output from repeated runs.

Add an end-to-end test against the provided PDF and ground truth.

Run the full test suite and fix any failures.

## 8. Generalization and robustness

The sample is only one page, so do not claim that it proves generalization to arbitrary PDFs.

Include a short discussion of:
- Scanned versus digitally generated PDFs.
- Variable column counts and multiple reporting periods.
- Multi-page tables.
- Merged cells and wrapped labels.
- Japanese fonts and OCR errors.
- Financial notation and negative values.
- Hierarchical headings and repeated labels.
- Cases requiring a vision-language model.
- Confidence scores and human review for uncertain cells.

If practical, introduce a model-independent extractor interface so that another table extraction engine can be added without rewriting normalization and evaluation.

Do not train a model on a single page. Do not introduce a complicated agent framework, database, web server, or frontend unless there is a clear benefit.
